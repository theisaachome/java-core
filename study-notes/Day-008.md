SOLID represents five design principles for object-oriented software development intended to make code readable, maintainable, scalable, and easy to extend without breaking existing behavior.

---

## 1. Single Responsibility Principle (SRP)

### Keynote
A class should have **one, and only one, reason to change**. It should focus on a single job, component, or capability.

### Real-World Scenario
An `OrderService` class that processes order workflows, calculates payment amounts, triggers payment transactions, sends customer notification emails, and dispatches shipping details violates SRP. If database schemas, email services, payment gateways, or shipping logistics providers change, this single class requires modification.

Separating these concerns into `PaymentProcessor`, `EmailService`, `ShippingService`, and using `OrderService` strictly for orchestration ensures each component has a single reason to change.

### Bad Implementation
```java
// BAD: Class has multiple reasons to change (Order handling + Payment + Email + Shipping)
public class OrderService {
    public void placeOrder() {
        System.out.println("Order placed successfully");
    }
    public void processOrder() {
        System.out.println("Processing order");
    }
    public void processPayment() {
        System.out.println("Processing payment");
    }
    public void sendEmail() {
        System.out.println("Sending email");
    }
    public void shipOrder() {
        System.out.println("Shipping order");
    }
}
```
### Good Implementation (Refactored to SRP)
```java
// GOOD:
// 1. Dedicated Payment Class
public class PaymentProcessor {
    public void processPayment() {
        System.out.println("Processing payment");
    }
}

// 2. Dedicated Email Class
public class EmailService {
    public void sendEmail() {
        System.out.println("Sending email");
    }
}

// 3. Dedicated Shipping Class
public class ShippingService {
    public void shipOrder() {
        System.out.println("Shipping order");
    }
}

// 4. Orchestration Class with Injected Dependencies
public class OrderService {
    private final PaymentProcessor paymentProcessor;
    private final EmailService emailService;
    private final ShippingService shippingService;

    public OrderService(PaymentProcessor paymentProcessor, 
                        EmailService emailService, 
                        ShippingService shippingService) {
        this.paymentProcessor = paymentProcessor;
        this.emailService = emailService;
        this.shippingService = shippingService;
    }

    public void processOrder() {
        System.out.println("Processing order");
        paymentProcessor.processPayment();
        shippingService.shipOrder();
        emailService.sendEmail();
        System.out.println("Order placed successfully");
    }
}
```


## 2. Open/Closed Principle (OCP)

### Keynote
Software entities should be open for extension, but closed for modification.
You should be able to add new functionality without altering existing, tested code.

### Real-World Scenario
An e-commerce payment module using if/else or switch blocks to process Credit Card or PayPal payments requires modifying original source code every time a new payment provider (e.g., Apple Pay, Crypto) is introduced. 
Using an interface allows adding new payment processors seamlessly without editing core checkout logic.


### Code Example
```java
// Interface allows extension without code modification
interface PaymentMethod {
    void process(double amount);
}

class CreditCardPayment implements PaymentMethod {
    public void process(double amount) { System.out.println("Paid via Credit Card: $" + amount); }
}

class CryptoPayment implements PaymentMethod { // Added without touching existing code
    public void process(double amount) { System.out.println("Paid via Crypto: $" + amount); }
}

class CheckoutService {
    public void checkout(PaymentMethod paymentMethod, double amount) {
        paymentMethod.process(amount); // Closed for modification, works with any implementation
    }
}
```


## 3. Liskov Substitution Principle (LSP)
### Keynote
Subclasses must be substitutable for their base classes without altering the correctness or breaking expected behaviors of the program.

### Real-World Scenario
A Square class extending a Rectangle class breaks expectations if setting width on Square implicitly mutates its height.
Callers expecting generic Rectangle behavior will experience bugs. Similarly, creating an Ostrich class that inherits from a Bird class with a fly() method forces Ostrich to throw runtime exceptions.

### Code Example
```java
// BAD: An Ostrich is-a Bird, but throws an exception on fly(), breaking LSP
abstract class Bird {
    public abstract void fly();
}
class Ostrich extends Bird {
    @Override
    public void fly() { throw new UnsupportedOperationException("Ostriches cannot fly!"); }
}

// GOOD: Separate concerns into capabilities so subclasses remain fully substitutable
abstract class Animal {}

interface Flyable {
    void fly();
}

class Eagle extends Animal implements Flyable {
    public void fly() { System.out.println("Eagle flying high"); }
}

class Ostrich extends Animal {
    public void run() { System.out.println("Ostrich running fast"); }
}
```

## 4. Interface Segregation Principle (ISP)
### Keynote
Clients should never be forced to depend on interfaces or methods they do not use.
Prefer smaller, focused interfaces over large, fat ones.

### Real-World Scenario
A MultiFunctionPrinter interface containing print(), scan(), fax(), and staple() forces a basic StandardPrinter class to implement dummy scan() or fax() methods throwing exceptions.
Splitting into Printer, Scanner, and FaxMachine interfaces ensures classes implement only relevant capabilities.

```java
// Split fat interface into lean, client-specific contracts
interface Printer {
    void print();
}

interface Scanner {
    void scan();
}

// Basic printer only implements what it actually supports
class SimplePrinter implements Printer {
    public void print() { System.out.println("Printing document..."); }
}

// Advanced all-in-one printer implements multiple interfaces
class AdvancedOfficePrinter implements Printer, Scanner {
    public void print() { System.out.println("Printing document..."); }
    public void scan() { System.out.println("Scanning document..."); }
}
```

## 5. Dependency Inversion Principle (DIP)
### Keynote
High-level modules should not depend on low-level modules; both should depend on abstractions.
Abstractions should not depend on details; details should depend on abstractions.

### Real-World Scenario
A high-level NotificationService that directly instantiates a concrete EmailClient inside its constructor cannot easily switch to SmsClient or inject mock dependencies for unit testing.
Injecting an abstract NotificationChannel interface decouples the high-level business logic from low-level delivery details.

```java
// Abstraction contract
interface NotificationChannel {
    void send(String recipient, String message);
}

// Low-level details implementing abstraction
class EmailChannel implements NotificationChannel {
    public void send(String recipient, String message) {
        System.out.println("Email to " + recipient + ": " + message);
    }
}

class SmsChannel implements NotificationChannel {
    public void send(String recipient, String message) {
        System.out.println("SMS to " + recipient + ": " + message);
    }
}

// High-level module depending strictly on abstraction (Injected via Constructor)
class UserNotificationService {
    private final NotificationChannel channel;

    public UserNotificationService(NotificationChannel channel) {
        this.channel = channel; // Flexible component injection
    }

    public void notifyUser(String user, String msg) {
        channel.send(user, msg);
    }
}
```
